## 摘要

这是一个面向中小型装修公司**经营全流程**的数字化管理平台，采用模块化单体架构：一个代码仓库、一套平台外壳、一份共享主数据、九个可插拔功能区。

平台的主脊已经打通并真实联动：**线索 → 签约建项 → 设计 → 报价与变更 → 工序排程 → 验收与整改 → 回款 → 经营看板**。它替代的不是某个软件，而是"Excel 报价单 + 微信群里的现场照片 + 口头汇报的进度 + 月底对不上的账"这套组合。

三个可作为对外承诺的技术特征：**口径单点**（全公司的金额算法只存在于一处，被脚本反复复算校验）、**派生值不落库**（进度、灯色、解锁状态是算出来的，不是录进去的，因此不会互相打架）、**核心账籍没有硬删除**（报价、收支台账、验收节点只有归档与恢复，误操作可逆；变更单、科目模板、字段定义这类修正与配置数据提供删除操作）。

当前形态是**免登录单用户内测**，不是多员工并发生产环境。这一条在所有对外材料里都应保留。

## 一、建设背景：要解决的是五处管理损耗

装修经营的管理难度不在单点专业度，而在**信息跨环节传递时持续失真**。公司在手项目几十个，每个项目要穿甲方、房屋、设计、预算、施工、验收、收付款七类信息，一旦这些信息分散在不同载体上，就会固定产生五类损耗：

**工期失控，且业主不透明。** 排期在设计师和项目经理各自的表里，工序之间的先后关系靠人记。哪道工序晚了、会不会顶到合同完工日，通常等到延期已成事实才被发现。

**质量无据可查，纠纷举证难。** 验收结论往往是口头或微信里的一句"过了"。事后争议时，拿不出"哪天、按哪些检查项、由谁验收、当时现场是什么样子"的成串证据。

**预算跑偏，成本黑箱。** 报价、变更、实际支出是三张分离的表。变更做了多少、是否已经顶穿合同额、这个项目到底还剩多少毛利，需要有人在月底手工拼一次，且拼出来的口径每次都不太一样。

**人效低下，绩效无数据支撑。** 谁在做几个项目、承担什么责任、返修率高不高，全凭印象。

**线索流失，商务管理混乱。** 谈过的客户散落在销售的微信里，跟进断没断、报价了没报价、报完价签没签，公司层看不到。

这五点是本平台立项文档里的原始问题清单，不是事后总结。因此平台的推进逻辑也很明确：**先修通"客户线索 → 项目 → 签约"这条主脊，随即投入执行链（设计 → 工程 → 质量）去治工期与质量失控，财务与绩效随后接上**——而不是先做一个漂亮的数据大屏。

还有一条更具体的背景值得写下来。本平台的第一个版本并不是代码，而是一套无代码平台搭出来的多维表格原型。它把业务字段和表单跑通了，随后撞到四堵墙：公式列的计算性能随数据量下降、公开视图不支持附件、外部人员无法登录、没有可用的自动打印能力。这四堵墙得出了一个对项目边界很重要的结论：**能填表和能管理是两件事，"资料"和"系统"之间差的正是跨表联动、口径一致与证据留存。**2026-10-09 起，平台按这份蓝图重建为真实应用。

## 二、平台定位

**一句话定位：** 装修经营全流程的数字化管理平台——一个仓库、一套外壳、共享主数据、可插拔功能模块。

**架构定位：模块化单体。** 未来加入「项目管理系统」「设计管理系统」等能力时，它们长成平台里的一个功能区，共享同一份登录、主数据与视觉语言，而不是另起一个系统再拼进门户。平台对此有明确的红线：**不做微前端、不做多系统拼门户、不在第一个模块阶段做重型权限中台。**

**业务定位：首期主打数字化经营管理，不预设 AI。** 平台的价值来自流程与数据口径的收敛，而不是模型调用。AI 辅助管理被明确排为后续方向（DEFERRED），当前命名与界面均不强调 AI。

**当前使用形态：** 单用户、免登录。数据表与 11 个业务角色常量（分属管理 / 商务 / 设计 / 工程四条业务线）已经预留，但权限收敛排在登录批次，现阶段"角色"是数据字段与看板视角，**不是安全边界**。任何对外材料都不应把角色说成已具备的权限隔离。

**四条数据观。** 这四点决定了平台的性格，也是内部汇报时最值得讲的部分：

- **不设硬删除入口。** 报价、台账、验收节点都是长期对账依据，SQLite 也没有回收站，因此"误操作能纠正"一律走归档与作废，恢复时必须回到归档前那一态。
- **归档不改变事实。** 口径为"**钱按事实 · 事按可见性**"：已收、支出、合同额、累计变更、毛利、现金线、签单额**含已归档项目照算**（发生过的事不因归档消失，否则历史月份的收款线会凭空掉一截）；待收款、未整改问题、待办、风险计数、健康度等**前瞻类排除已归档**（归档意味着经营事项已收场）。两族口径不同是有意的，因此相关页面自己会把差异说出来。
- **算不出就写算不出。** 面积未录则单方造价不显示；支出未录则毛利率降级为"不可算"而不给 100%；某月没有现金往来则显 0 而非留空。宁可缺一格，不造一个数。
- **派生值不落库。** 进度、风险灯、付款段解锁状态都由原始数据实时算出。少存一处，就少一处会腐烂的地方。

**明确不做的：** 行业多租户 SaaS、面向业主的商城或门户、工地物联网与摄像头接入、运行时插件系统与沙箱（在真实触发条件出现前，插件化只是方向标而非施工图）。

## 三、整体架构

### 3.1 分层结构

| 层 | 位置 | 职责 | 约束 |
|---|---|---|---|
| 路由层 | `src/app/**` | 页面渲染、参数解析、表单提交入口 | 刻意做薄，不写业务逻辑 |
| 模块层 | `src/modules/<id>/` | 单个功能区的业务逻辑与私有数据访问 | 只经 `core` 与注册表协作，不互相 import 内部实现 |
| 共享核心 | `src/core/` | `domain` 主数据与全局口径 / `ui` 基础组件 / `db` 连接单例 | 跨模块唯一通路 |
| 数据层 | `prisma/` | schema、迁移、演示数据 | schema 保持可移植，便于一步迁 PostgreSQL |

**可插拔机制。** 每个功能区在自己目录下导出一个 `ModuleManifest`（id、名称、描述、排序、入口路径、可选二级导航），`src/modules/registry.ts` 汇总成唯一清单，平台外壳的侧栏导航与首页入口卡**只读这张表**，不写死任何模块。新增一个功能区 = 建一个目录 + 在清单里加一行。这条机制已被两次真实验证：自定义字段、人员工控上线时，外壳与首页代码零改动。

### 3.2 技术选型及理由

Next.js（App Router）+ TypeScript 全栈一体，页面与 Server Action 同仓，避免前后端两套构建与一次额外网络跳转；Prisma ORM + **SQLite** 起步，schema 保持可移植（禁用 PostgreSQL 专有类型、枚举用字符串常量），上多用户并发时一步迁 PostgreSQL；pnpm 管包；Tailwind 仅作原子工具类，视觉规则从设计系统派生成一层 CSS 变量令牌（`src/styles/tokens.css`）。

**不引入任何成套组件库、不引入图表库。** 按钮、卡片、输入、表格、弹窗、抽屉、徽标、导航、顶栏、通知铃共 10 个基础组件在 `src/core/ui/` 手写；驾驶舱的月度现金折线与工序甘特图都是手绘 SVG。换来的是完全可控的视觉密度、零依赖漂移，以及单运行时、少进程、省内存——部署目标是 2G 内存的轻量服务器。

SQLite 有一处实测限制值得记录：本栈（Prisma 5.22 + SQLite）不支持 `Json` 类型。因此自定义字段的多选项采用"每行一个选项"的纯文本约定，需要结构化的地方在**服务层单点解析**，而不是到处塞 JSON 字符串。

### 3.3 数据模型

**28 个业务实体、12 条增量迁移**（每条迁移只加列或加表，历史数据零破坏）。实体分三层：

- **共享核心域**（唯一真源，禁止任何模块重复定义）：`Organization`、`User`、`Client`、`Project`、`ProjectMember`。
- **功能区自有表**：预算（`CatalogCategory` / `CatalogItem` / `BudgetQuote` / `QuoteItem` / `ChangeOrder`）、线索（`Lead` / `FollowUp`）、设计（`DesignTask` / `TaskSubmission`）、排程（`ProcessTemplate` / `ScheduleTask` / `ScheduleTaskDependency`）、质量（`CheckItem` / `AcceptanceNode` / `NodeCheck` / `Issue` / `Evidence`）、财务（`FinanceRecord` / `PaymentNode`）。
- **平台横切表**：`CustomFieldDef` / `CustomFieldValue`（自定义字段）、`PlatformSetting`（主题与品牌）、`OperationLog`（操作流水）。

**一条铁律撑起整个闭环**：所有功能区的业务表都必须经 `projectId` 挂在 `Project` 上，**任何模块不得自建"项目"实体**；客户维度经 `Project.clientId` 间接关联，不得绕过项目直接绑客户。对内关联与深链用 `Project.id`，对外展示与对账用人类可读的 `Project.code`（`RP-YYYY-NNN`）。因此"一个项目的全部经营数据"在设计上就是可以被一次查询收齐的——项目中心六合一详情页正是这一条的落地。

**口径文件单点**：报价算式只在 `core/domain/pricing.ts`，钱的口径只在 `core/domain/ledger.ts`，进度与三色灯只在 `core/domain/health.ts`，驾驶舱聚合只在 `core/domain/dashboard.ts`，付款段模板与解锁派生只在 `modules/finance/payment.ts`（付款计划的物化与门控服务在 `server/payments.ts`），跨模块整合器只有 `core/domain/acceptance.ts` 一处。

### 3.4 视觉系统

界面遵循 `HAE Creator Design System V0.3`：纸感底色、全画面单点强调色、气声描边、默认无阴影，层级靠字重与对比度而非字号和粗线。字号只用 12/13/15/17/20/28px、间距只用 4/8/12/16/24/32/48px，是写进项目契约的硬约束。

主题能力已上线：四套预置强调色插槽（钴蓝默认 / 铁锈红 / 祖母绿 / 青）在平台设置页自助切换，**数据库只存插槽键名、不存自由色值**，也不开取色器——需要新配色时走规范补一套，而不是现场调色。

启动首页是视觉契约的**成文例外**（展示级字号、深色主按钮、径向柔光、入场动画），例外被严格锁在一个 CSS 作用域内，业务页不得引用；配色仍全部取平台令牌变量，换主题时首屏跟着换。

### 3.5 质量工程

一个要被交付使用的管理系统，可信度来自验证手段。当前有三层：

| 层 | 内容 | 规模 |
|---|---|---|
| 纯函数门禁 | 直接 import 生产代码，用独立预言机（整数分复算）交叉比对算法结果 | 11 个脚本，覆盖报价、财务、质量、排程、设计、线索、驾驶舱、自定义字段、健康度、主题、人员 |
| 集成门禁 | 打隔离临时库，真跑生产服务函数，验事务传播与状态机守卫 | 5 个脚本（签约建项、排程生成、质量流程、财务流程、证据上传） |
| 交互写回验收台 | **无头浏览器真实点击** → 服务端接收 → 落库 → 回读页面，三方对账；全程打副本库，收尾元断言实库未被写过 | 12 个套件 |

最近一次全站验收（2026-10-13）：**PASS 287 / FAIL 7 / NOTE 5**，7 条未通过项逐条核实后全部是测试脚本自身的预期或定位错误，**未留下任何未修的产品缺陷**。更重要的是这套手段确实抓到过真实缺陷：科目库一度没有"新增科目项"入口（历史缺陷，构建绿灯与截图都没拦住）；归档后恢复项目会错落"草稿"态；设置页四套主题卡显示同一颜色；两处文案与新口径矛盾。这些缺陷的共同点是**编译期与构建期全都发现不了**。

同时，平台把"逻辑问题只能在真实使用中暴露"当成了前提来建设：全站 51 处 catch 中的 48 处统一写入**错误现场日志**（JSONL；另 3 处为日志器自身兜底、并发转换重试与文件清理，有意不记。生产构建下可用页面上的错误编号反查），所有关键写操作统一经 `recordOperation()` 记**操作流水**（best-effort，记流水失败绝不把业务写入带下水）。员工说"这个数上周还不是这样"或"页面打不开"时，现场是可以被重建的。

### 3.6 部署路线

当前在本机与内网运行，仓库内尚无容器与反代配置文件，因此**部署能力属于规划项而非已具备能力**。既定路线分两段：**极空间 NAS 局域网内测**（单 Web 容器 + 反向代理，保持 SQLite，每日数据库备份与快照，暂不开放公网）→ **阿里云轻量服务器正式环境**（Docker Compose：应用 + Caddy 终止 HTTPS，文件走 OSS；并发条件出现时一步迁 PostgreSQL）。迁移顺序为：文件存储抽象 → NAS 内测 → OSS 适配 → 登录与权限 → PostgreSQL。

## 四、核心业务模块

九个功能区，按侧栏导航顺序：

| # | 功能区 | 路径 | 解决什么 | 完成度 |
|---|---|---|---|---|
| 01 | 数据驾驶舱 | `/dashboard` | 老板一页看清经营事实与需要处理的事 | 已上线 |
| 02 | 商务线索 | `/crm` | 线索不流失、跟进不断线、签约即建档 | 已上线 |
| 03 | 项目管理 | `/projects` | 一个项目的全部经营数据在一处 | 已上线 |
| 04 | 设计管理 | `/design` | 设计任务有状态、有版本、有返修记录 | 已上线（缺任务新建入口） |
| 05 | 时间管控 | `/schedule` | 工序排程、工期预警、进度回填 | 已上线 |
| 06 | 质量管控 | `/quality` | 验收有据、问题整改闭环 | 已上线 |
| 07 | 装修预算报价 | `/budget` | 报价可复用、可算、可打印 | 已上线（首个模块） |
| 08 | 财务管控 | `/finance` | 收支台账、付款计划、毛利粗算 | 已上线 |
| 09 | 人员工控 | `/hr` | 人员档案与项目责任关系 | 首单元进行中 |

### 4.1 数据驾驶舱

聚合首页，全部只读、不做任何二次录入。主指标带是**本月签单额（含环比）、在建项目数、全司回款率、风险项数**（风险按工期 / 质量 / 预算 / 变更四类细分，只数红灯）。往下依次是「需要你处理」清单（按数量倒序，每组最多三条可点开的深链）、项目健康度密集矩阵（状态、进度、三色灯、合同额、已收、毛利、毛利率、风险，点行进项目中心）、近六个月现金收付折线与逐月净额表、项目毛利率排行、商务漏斗与签约率。

几条口径值得单独说明，因为它们是"不造数"的具体体现：签单额只统计**由签约建项而来**的项目（手工补录的项目不算签单）；回款率分母是**合同额加累计变更**而非合同额；毛利率排行把"未录入支出"的项目**移出榜单**而不是显示 100%；漏斗只画各阶段存量分布，**不画相邻阶段转化率**——因为平台没有阶段停留流水表，画出来就是假日绩指标。人效排行当前是一张明确的灰占位卡，等人员工控补齐数据后转实。

### 4.2 商务线索

线索五阶段：**线索 → 已联系 → 已确认 → 已报价 → 已签约**。看板支持卡片拖到**相邻后一列**推进；已报价阶段不再给通用推进按钮，只能走"签约建项"——这一条是收紧过的，防的是随手拖出一个没有合同额、没有项目的悬空"已签约"。超三天未跟进的线索标红，跟进记录带下次跟进日期。

**签约建项是全平台价值密度最高的一次动作**：录入合同额、设计师、项目经理、开工日期并点击签约，在一个事务里自动完成四件事——按手机号归并或新建客户、创建项目（自动编号）、生成这张项目的空报价单、回写线索与项目的 1:1 来源关系。签约不可逆、无删除入口，作废线索的守卫在服务层：已签约的线索不许只作废线索，那会让项目失去来源。

### 4.3 项目管理

列表支持卡片 / 表格双视图、状态筛选、**按自定义字段筛选**（命中为零就返回空列表，绝不悄悄退化成"无筛选"）。核心是**六合一详情页**：基础信息、设计进度、工期进度、质量验收、预算收支、人员分配，六个 Tab 一次性把六个功能区在这个项目上的现状收齐，每一格都能跳回源模块。另有「项目动态」页按时间回放该项目的操作流水（23 类动作有中文名，项目新建、签约建项、证据上传、责任关系变更等暂显示为「项目操作」，标签映射待补齐；均含操作人与变更前后）。

归档入口有两处，确认框会**如实列出未闭环事项**（未整改问题数、未收付款段数与金额）——归档合法，但要知情。

### 4.4 设计管理

设计任务五状态（待分配 / 进行中 / 待审核 / 待返修 / 已通过），双视角（设计任务池 / 指派给我），看板与日历两种排布，日历按截止日归组色片并诚实提示"未排期 N 条"。任务详情支持执行者提交成果（提交说明必填、交付物链接需 http(s) 校验）、完整版本历史（版本号、提交人、退回原因、审核人与时间）、以及审核动作：通过，或**退回必填原因**。返修率与平均返修轮次口径已实现，暂未渲染到页面。

**必须说清的边界**：交付物目前是链接而非文件上传（界面已注明占位）；设计任务目前**没有新建与指派入口**，数据来自演示数据批次——这是主脊上已知最明确的一处断点，排在后续批次。

### 4.5 时间管控

**一键排程**：按项目建筑面积自动落到面积档（90㎡ 以下 / 90–130㎡ / 130㎡ 以上），取该档的 11 道工序标准天数模板，按链式关系排出起止日期并写入工序依赖；模板不齐、面积未录、开工日缺失三种情况**不生成**，并给出人话原因。工序标准天数在「工序模板库」按面积档维护（每格 1–999 天），改天数不回溯已生成的排程。

**甘特视图**左侧工序列表带进度小字与逾期标记，右侧计划条与实际进度双轨、依赖肘线、今日线；**拖拽计划条可整体平移调期**。在任务抽屉里改计划起止、指派负责人、更新进度 0–100。超期看板按已逾期 / 预警 / 正常 / 未排程四区分发。

进度不是装饰：拉到 100% 会在同一事务里补写实际完工日，并**自动触发质量模块生成验收节点**；回落到 100% 以下则把尚未提交的验收节点收走。工序依赖目前由一键生成产生线性链，暂不支持手工编辑。

### 4.6 质量管控

**验收节点**由排程完工自动生成，检查项按工序阶段从标准检查项库快照下来（同一工序该查什么，全网一致，不靠个人习惯）。提交时逐项判"过 / 不过"并附说明与现场照片；审核**退回报原因必填且必须指定严重度**。退回的同时，系统在同一事务里**自动创建一条质量问题**，节点进入"整改中"并禁止再提交，直到关联问题全部整改完成。问题台账走"整改 → 复验 → 关闭 / 复验退回"三态，可按项目、状态、严重度筛选。

**现场证据**是这一环的长期价值所在：节点级照片上传（服务端重命名、类型与大小双重校验、拒绝路径穿越、单张 ≤5MB、每节点 ≤9 张、仅上传者本人可删、操作写流水）。「质量档案」把每个项目的节点生成、提交、通过、退回与问题创建、整改、关闭串成一条垂直时间轴，并提供 A4 打印版。**这份可打印档案就是纠纷时能拿出来的东西。**

检查项目前由演示数据批次维护，尚无编辑界面。

### 4.7 装修预算报价

先有**工程科目库**（科目分类 + 科目项模板，含单位、默认单价、默认数量、材料构成、施工工艺 SOP），再有报价。编制时从科目库搜索选入，生成**快照明细行**而非引用——这一条很关键：**改模板不会回头篡改任何历史报价**，已交付出去的对账依据保持稳定。行内可改编号、名称、单位、单价、数量，可增删行、上下排序，保存走整表替换并有脏状态提示。

实时汇总条显示直接费、税金（默认 3%）、**单方造价**（面积缺失时明确显示"面积缺失"而非估算）、总价。另有科目分布页（占比条 + 填报完整度，缺材料 / 缺 SOP 的行数被点出来）与**A4 打印视图**（封面、费用汇总、分科目明细含材料与工艺、甲乙双方签字栏）。报价明细上另有**变更单**：增项 / 减项 / 升级 / 工艺四种类型，方向有守卫、金额带符号、累计变更超合同额 5% 触发预警并联动财务毛利与预算灯。

### 4.8 财务管控

**收支台账**双 Tab（收入 / 支出，类型与科目联动互斥），录入即复算。汇总条第一格是毛利润与毛利率色档（>25% 绿、≥15% 黄、<15% 红），其后五格是合同额、已收款、待收款、计划未付合计、总支出。**付款计划**按五段模板生成：开工款 30%、水电完成款 20%、主体完工款 30%（泥工 / 防水 / 地面 / 天花四道全过）、竣工验收款 15%、保修金 5%（竣工日 + 12 个月）。

三处设计值得单独讲，因为它们都是"宁可别扭也不出错"的选择：

1. **付款段的解锁状态是从验收结果算出来的**，不落库。未解锁的段，"标记已付"按钮禁用并给出缺哪道工序或保修期未到的具体原因。质量与钱就这样锁在一起了。
2. **两本账分离**：在付款计划里"标记已付"不会自动生成一条收入台账记录。页面上方因此有一条对照条（计划已标记 vs 台账实际入账，差额非零标黄），不静默对齐。
3. **前四段按比例算、尾差归末段**，保证五段之和恰好等于合同额，不出现"少了一分钱"。

台账目前无 CSV / Excel 导入导出；全站的数据输出能力是两处 A4 打印视图。

### 4.9 人员工控（首单元进行中）

已完成的是最基础的一块：人员档案（姓名、角色、部门、邮箱、参与项目数）复用共享的 `User` 表，并新增**项目责任关系**——把某人在某项目上承担的责任（项目经理 / 设计师 / 工程巡检 / 施工负责人 / 项目协调五种）的对应关系登记下来，同项目同人同角色唯一；责任关系的**起止时间与备注目前只有字段与列表展示，录入表单尚未开放**。

尚未开始的是工作记录与绩效算法。因此驾驶舱的人效排行仍是灰占位，且注册表里该功能区的描述含一项未实装内容（「基础工作记录」）——对外材料在补齐前不应宣称绩效能力。

### 4.10 自定义字段（平台横切能力）

不占导航位（入口在平台设置页），但它决定了平台的适配能力：公司要给项目加"复尺日期""保修年限""家电交付范围""交付备注"这类行业特有信息，不需要改代码或等排期。支持五种类型（文本、多行文本、数字、日期、单选），必填闸门、值按类型分列互斥存储（避开 SQLite 对字符串列做区间比较时按字典序出错这个坑）、停用优先于删除。**当前只作用于项目与客户两类对象，明确不开放给报价明细行**——因为报价保存走整表替换、行 id 每次重分配，挂在明细行上的字段值会在保存时静默变成孤儿。项目侧已完整可用（录入 + 列表筛选），客户侧只留了数据位、无界面。

                    │                     ↓                            ↓

### 5.2 数据流转矩阵：每个数据域由谁产生、被谁消费

| 数据域 | 落在哪 | 谁写入 | 谁消费（含自动联动） |
|---|---|---|---|
| 客户 | `Client` | 线索签约时按手机号自动归并；项目表单可就地改名 | 项目列表与详情；改名连带该客户全部项目显示（有意行为，表单明确提示副作用） |
| 项目 | `Project` | 签约建项自动生成，或在预算模块手工建档 | 九个功能区的唯一挂载点；驾驶舱在建数与签单额、财务口径、归档可见性 |
| 设计 | `DesignTask` / `TaskSubmission` | 目前仅演示数据批次（缺新建入口）；提交与审核由功能区写入 | 项目中心设计 Tab（状态计数与逾期）；返修率口径待渲染 |
| 预算 | `QuoteItem` / `ChangeOrder` | 报价编辑器整表替换；变更单录入即生效 | 项目中心预算 Tab（四算 + 分科目占比）；变更后总额进入财务毛利与预算灯 |
| 施工 | `ScheduleTask` / 依赖边 | 一键排程生成；甘特拖拽与进度回填修改 | 驾驶舱工期风险；项目中心工期 Tab；**进度 100% → 跨模块生成验收节点** |
| 验收 | `AcceptanceNode` / `NodeCheck` / `Evidence` | 排程完工自动生成节点；现场提交与审核 | **节点通过 → 付款段派生解锁**；退回 → 自动建问题；质量档案时间轴与打印 |
| 问题 | `Issue` | 审核退回自动创建，或手工登记 | 项目与节点被锁住不许提交；复验通过才能关闭；未整改数进风险与待办、并出现在归档确认框 |
| 回款 | `PaymentNode` | 按合同额与五段模板生成；标记已付受验收门控 | 待收款（前瞻类，排除已归档）；与台账已收对照显差额 |
| 收支 | `FinanceRecord` | 台账手工录入 | 毛利、毛利率、净现金、月度现金线、全司回款率 |
| 主数据扩展 | `CustomFieldDef/Value` | 平台设置页定义，项目卡录入 | 项目列表筛选与深链、详情页展示 |
| 行为痕迹 | `OperationLog` | 关键写操作的动作层统一埋点 | 项目动态回放页；**归档前状态的恢复依据**；通知与错误日志互补 |

### 5.3 一条数据的完整旅程

下面是一次**走查示例**（数字为示意，用于说明联动关系，不是演示库里的实际值；演示库的真实规模为 8 个项目 / 12 条线索 / 33 道工序 / 23 个验收节点）：一个手机号进入线索库 → 三轮跟进推到已报价 → 点签约，填合同额 12 万、设计师、项目经理、开工日 → 系统建好客户、项目 `RP-2026-005`、一张空报价单 → 预算员从科目库选入 42 条明细，实时看到直接费、税金与单方造价，导出 A4 与客户签字确认 → 施工期增了一条"瓷砖升级"变更 +8,600 元，累计变更超合同额 5%，报价与财务两处同时变黄 → 项目 105㎡ 落入 90–130 档，一键排程生成 11 道工序 76 天链式计划 → 泥工工序进度回填 100%，系统自动建出"泥工与防水验收节点"并挂上标准检查项 → 巡检上传 6 张现场照片，三项不过、审核退回并选"严重" → 自动生成质量问题，节点锁住不许提交 → 整改说明提交、复验通过关闭 → 竣工验收款 15% 段因验收通过解锁，财务标记已付；页面对照条提示"计划已付比台账多 3 万元，请核" → 老板在驾驶舱看到这个项目已进毛利排行、回款率与现金线同步更新 → 交房一年后保修金 5% 到期解锁，项目归档；归档之后，历史月份的收款线一格没少，但这个项目的待收款和未整改问题不再出现在任何待办视野里。

### 5.4 闭环目前到哪里为止

诚实的答案是：**到"回款 + 保修金账期"为止。** 严格意义上的售后段——客户回访、满意度、维修工单——尚未建，平台里承载它的只有一个数据机制（保修金 5% 在竣工 + 12 个月解锁）和一个字段位。这三项已排进后续路线。

另有五处已在册、不掩盖的闭环弱点：付款段与检查项对工序的匹配走**名字而非 id 外键**（工序改名会让付款段静默失配、永不解锁）；派生值不落库导致**没有"何时变红、何时解锁"的历史时间线**（操作流水部分补上了这一点，但状态变迁仍缺）；变更单**录入即生效**，尚无客户确认的审批状态机；设计环节缺任务新建与指派入口，是当前链路上最明显的断点；以及一处已长期登记的口径分叉——净变更为负时，毛利润把负变更按 0 计、而预算灯与回款比例使用带符号原值，两者会出现不一致（当前无数据触发，改动牵动 135 条断言基线，故保持现状并登记）。

## 六、数字化能力（横向）

这些能力不属于任何一个功能区，却决定了前九个功能区加起来是否可信。

**口径一致。** 全公司关于钱的算法只有四五个自包含的纯函数文件，被独立预言机在整数分维度反复复算，并有跨源不漂移护栏（驾驶舱现金线 ≡ 财务台账合计，由 86 条断言锁死）。这直接消灭了"两个页面同一个指标对不上"这一类最常见的信任崩塌。

**跨模块联动，而不是数据搬运。** 排程完工生成验收节点、验收通过解锁付款段、审核退回创建问题、变更影响毛利与预算灯——都是**读侧算出来的因果关系**。没有一处靠"人工记得去另一个模块录一遍"。

**可配置的字段层。** 五种类型的自定义字段 + 值按类型分列存储，让客户特有信息不需要改代码就能长出来，且筛选可深链分享。

**可逆的归档与知情确认。** 无硬删除、归档确认框列出未闭环事项、恢复回到归档前那一态（原值从操作流水回读），并在页面上说明"为什么这个数字含已归档项目"。

**行为与故障留痕。** 操作流水唯一入口 + best-effort 不影响业务写入；错误现场 JSONL 双写（标准输出与文件），生产构建下页面上的错误编号可反查现场堆栈。这两件东西在系统交给内部同事真实使用后，是排查"上周还不是这样"和"页面打不开"的唯一手段。

**风险聚合而非消息推送。** 通知中心按五组待处理事项（待审核验收、未整改问题、工期超期、变更超 5%、到期该跟进的线索）实时聚合，每条带深链。它是按需计算的，不是把消息塞进另一个聊天软件——这与"减少工具数量"的定位一致。

**证据与交付物输出。** 节点级现场照片留档（含上传归属与类型大小校验）、报价与质量档案两处 A4 打印视图（真 PDF 分页实测）。对装修行业，可打印的、带签字栏的、含工艺说明的文件仍然是一线真正用得上的输出形态。

**品牌与视觉一致性。** 设计系统首次落成 CSS 变量令牌；四套强调色插槽由数据库驱动全站切换、双声明锁防漂移；字号与间距阶梯写进契约；启动首屏作为成文例外被锁在单一作用域内。

**演示数据的严肃性。** 演示数据本身按可被验收的规格生成：幂等（重复跑不脏库）、自带断言（真实入库行数与预期不符即抛错）、并刻意留下反例位（一个必填字段留空的项目、无现金往来的月份显示 0），为的是让空态和降级态在演示时就是可见的，而不是一上线才崩。

## 七、角色价值

**先说边界**：平台当前免登录单用户，所以下表描述的是**每个岗位进场后能从这套系统拿到什么**，不是"该岗位已有自己的账号和权限"。真正的分权限排在登录批次。

| 角色 | 今天能得到的 | 关键价值 |
|---|---|---|
| 老板 / 经营 | 一页看清本月签单与环比、在建数、回款率、风险；项目健康度矩阵与毛利排行；现金折线；漏斗；六组待办（另有一组人效为灰占位）；按项目回放操作流水 | 从"月底等人报数"变成"随时自己看，且每个数都算得清"；毛利排行不再被无成本数据的项目虚高误导 |
| 商务经理 | 线索看板与拖拽推进、超三天未跟进标红、跟进时间线、一次签约生成客户+项目+报价单 | 线索不再随微信沉底；签约不再重复录入四遍；谈过的客户有归属和来源 |
| 项目设计师 / 设计线 | 任务池与自己名下任务双视角、日历排布、成果版本历史、审核退回原因必填 | 需求、版本、退回原因在同一处，返修不再靠聊天记录重演；截止日与逾期一目了然（待补任务新建入口） |
| 项目经理 | 一键排程、甘特拖拽调期、进度回填、超期与预警四区、项目中心工期 Tab | 排期从个人表格变成公司可查的计划；延期在顶到合同日之前就被点名；进度只需回填一次，验收自动跟上 |
| 工程巡检 / 质检 | 标准检查项逐项验收、退回即自动生成问题、整改复验闭环、现场照片留档、可打印质量档案 | 验收有据、举证有力；"改完没改完"不再靠嘴；质量问题不会在口头沟通里蒸发 |
| 预算员 | 工程科目库模板复用、报价编辑器、实时直接费 / 税金 / 单方造价、科目分布与填报完整度、A4 打印 | 报价从逐字敲表变成选科目改数量；改模板不篡改历史报价；漏填材料与工艺被明确指出 |
| 财务 / 出纳 | 收支台账、录入即复算毛利与毛利率、五段付款计划与解锁门控、两本账对照差额 | 该收多少、按什么条件收、收到没有，由验收结果说话；差额被摆出来而不是被抹平 |
| 平台管理员 | 主题与 Logo 自助切换与上传、自定义字段定义与停用、功能模块注册 | 平台适配公司，而不是公司迁就平台 |
| 业主客户 | 暂未开放 | 客户中心、进度查询与在线确认在路线图上，未建 |

## 八、未来发展

### 8.1 进行中：人员工控（M12 系列）

按"小步、稳定、有用、可扩展"的节奏推进：先补齐工作记录与项目责任确认，再做绩效数据与算法，最后把驾驶舱的人效卡从灰占位转实。当前已合入的是人员档案与项目责任关系这一单元。

### 8.2 近期：把主脊上的断点接上

- 设计任务的新建与指派入口（当前链路上最明确的断点）。
- 变更单的审批状态机（草稿 → 待确认 → 客户确认 / 驳回 + 附件），替代现在的"录入即生效"。
- 付款段、检查项与工序之间从名字匹配改为主键外键，消除改名静默失配风险。
- 报价确认与锁定态接通（状态字段已在，界面尚未给出写入路径）、税率可编辑、报价多版本。
- 实际完工日自动回填，让工期红灯与保修金基准不再依赖计划日期回落。
- 交付物文件上传（设计成果目前为链接占位）、检查项编辑界面、数据导入导出（Excel / CSV）。
- 三处过时文案修正与通知深链的收尾（不影响业务正确性，但影响可信观感）。

### 8.3 中期：多用户与对外触点

- **真登录与角色权限**：`User` 表、11 个业务角色与 4 条业务线常量、操作人字段都已留位，届时统一收口当前各处使用的占位操作人。
- **移动端业主客户中心**：进度查询、验收在线确认、质量档案查看。
- **现场巡检打卡**与移动端数据录入。
- **满意度与售后回访回流**，把闭环从"回款 + 保修金"延长到真正的售后段。
- **通知自动化**（当前是按需聚合，未来可主动推送）与经营分析深化（利润分析、获客渠道归因）。

### 8.4 基础设施

极空间 NAS 局域网内测（当前最优先待决策项）→ 阿里云轻量服务器 + Caddy HTTPS + OSS 文件存储 → 出现多用户并发时一步迁 PostgreSQL，并把字段级权限一并纳入。

### 8.5 明确排在后面的

运行时插件系统与事件总线、插件 SDK 与沙箱、多品牌白标、微前端、多个独立系统拼门户——这些不是"没做"，是**在真实触发条件出现前不做**。AI 辅助管理作为后期方向保留，首期不主打：它不是当前的管理瓶颈，把流程和口径修通才是。

## 附录 B：当前版本的已知边界

被问到时应直接照此回答，不含糊：

1. 单用户免登录，角色字段不是权限边界，并发与多人使用未验证。
2. 未部署到公网；Docker、反向代理、HTTPS、OSS 均为规划项，仓库内无配置文件。
3. 设计任务无新建与指派入口（数据来自演示批次）；交付物为链接而非文件上传。
4. 人员工控只有首单元，绩效与工作记录未做；驾驶舱人效为灰占位卡。
5. 无 Excel / CSV 导入导出，数据输出为两处 A4 打印视图。
6. 售后段（回访、满意度、维修工单）未建；闭环止于回款与保修金账期。
7. 变更单录入即生效，无客户确认审批流。
8. 报价的"已确认 / 已锁定"状态在界面上不可写；税率固定 3% 不可改。
9. 通知中心不推送、按需拉取，且个别深链落地后不定位到具体记录。
10. 工序与付款段、检查项按名字匹配，改名会静默失配（已登记待改为主键外键）。
11. 少数属性有字段位与展示、无录入或自动回填：户型、巡检人、预算员、获客渠道、实际完工日，以及人员责任关系的起止时间与备注。
12. 一次未复现的自定义字段删除时报错已登记待查，未闭环。
