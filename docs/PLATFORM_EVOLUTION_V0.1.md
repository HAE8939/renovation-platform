# 平台演进方向 V0.1 — 插件化话题的单一裁决记录

> 版本：V0.1 · 2026-10-11 · 维护：QwenWork（集成者）· 决策人：HAE
> 目的：把《开放式数字化平台理念》（HAE，2026-10）翻译为**本项目当前阶段可执行的边界纪律与触发器**，并裁定 2026-10-11 外部审查（`docs/REVIEW_EXTERNAL_2026-10-11.md`）中与插件化相关的建议。
> 使用方式：后续每次「要不要做插件系统 / 事件总线 / SDK」的讨论，先读本文件；外部审查者与新加入的 AI 也应先读本文件再做评审——**已裁定的不再重开**。

## 1. 北向标（理念原话浓缩）

> 不再开发一个「功能固定的软件」，而是构建一个能够持续生长的软件平台。

1. Core 提供基础，Plugin 提供能力。
2. 平台定义规则，插件实现功能。
3. 能力通过标准接口进入平台。
4. 插件之间通过标准协议和事件协作。
5. 平台的价值不是拥有多少功能，而是能够承载多少未来的能力。

**本项目立场（DECIDED）**：理念是**北向标**，不是施工图。当前的振幅是「编译期插件化的垂直领域平台」；运行时插件生态（安装/启停/升级/第三方）等触发条件出现再立项（见 §3）。

## 2. 当前对应物映射

| 理念概念 | 本项目当前对应物 | 状态 |
|---|---|---|
| Platform Core | `src/core/`（domain / ui / db）+ `AGENTS.md` 契约 + 设计令牌 | 成立（垂直领域核心；身份/权限待 P4） |
| Plugin Runtime | `src/modules/registry.ts`（编译期注册，新增模块 = 加一行） | 有意的最小版 |
| Plugin Manifest | `ModuleManifest`（id / name / order / entryPath / nav） | 有意保持精简；不扩「能力/权限/事件声明」直到出现第二消费方 |
| Plugin（能力单元） | `src/modules/*`（清单 + 服务 + UI + 私有表；模块 ≠ 页面） | 成立 |
| 平台规则 | 四铁律 + 快照语义 + 状态机纯函数 + 诚实降级 + 门禁体系 | 成立 |
| Configuration | 无（`PlatformSetting` 计划 M9：主题键名插槽 + Logo） | M9 最小版 |
| Data Extension | 无（EAV 计划 M9：`CustomFieldDef`/`Value`，作用 Project+Client） | M9 |
| Permission / Identity | `rbac.ts` 骨架（当前免登录单用户） | DEFERRED → P4 |
| Event / Workflow / Lifecycle / SDK | 无 | DEFERRED（触发器见 §3） |

一句话对照：**模块已是「编译期插件」（有清单、有边界、有私有数据与服务），缺的全部是「运行时」能力。**

## 3. 差距清单与触发器（满足触发条件才立项，未触发不做）

| 缺口 | 裁定 | 触发器 |
|---|---|---|
| 运行时插件（安装/启停/升级/卸载/沙箱/依赖解析） | DEFERRED | 出现**第二个产品形态**（多公司/多租户/白标/对外售卖）或真实第三方开发需求 |
| 插件 SDK 与来源/版本协议 | DEFERRED | 同上，且出现非本团队的插件开发者 |
| 事件总线（Event Bus） | DEFERRED | ≥2 个真实的「通知/联动」消费者同时存在（例如通知系统要上线时） |
| 跨模块服务契约（取代「core 整合器」） | DEFERRED | 出现**第二个**模块私有表跨模块写入点，或项目中心聚合维护明显变痛 |
| 模块聚合接口（项目中心不直读各模块表） | EXPLORING | 并入上一条；下一个需要接入聚合的模块到来时评估 |
| 多组织数据隔离 | 绑定 P5 | 迁 PostgreSQL / 多租户部署时一并做 |
| 登录 / RBAC（身份与权限） | 既定 P4 | 部署到可访问网络前 |

## 4. 边界纪律（每个里程碑过一遍）

**三问**：

1. 新功能是否只动自己模块目录 + registry 一行？
2. 跨模块是否只走 core（`core/db` prisma 直读 + 口径调 `core/domain`），不 import 其他模块内部？
3. 口径/常量是否单点（页面与组件不各写算式）？

**两条护栏**：

1. 模块私有表的跨模块**写入点**全仓只允许一个（现为 `core/domain/acceptance.ts` 的 `syncAcceptanceNodes`，M7 登记在案）。出现第二个时必须先立机制（服务契约），禁止照抄第二个。
2. `core/` 不新增业务逻辑；「平台能力」（配置、自定义字段）落 `core` + 对应平台页，业务逻辑落模块。

## 5. 拒绝清单（已裁定，勿再提）

- 微前端、多独立系统拼门户（沿既有 REJECTED）。
- 在 §3 触发器出现前：不做运行时插件运行时 / 事件总线 / 插件 SDK / 沙箱。
- 不把 `Project` 业务字段迁出主脊（2026-10-11 外部审查曾建议，经裁定否决：Project 是垂直领域主数据脊柱，迁出会破坏共享模型、增加跨模块关联；只有本平台变为「多垂直行业通用平台」时才重新切片）。
- 不为「理念完整性」提前抽象（红线一/三：不过度设计、不提前实现）。
